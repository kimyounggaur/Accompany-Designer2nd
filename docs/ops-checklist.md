## 사람이 직접 듣고 확인해야 하는 것 (설계서 P3-5·P3-6 "수동 점검")

자동 시험은 가짜 마이크(헤드리스 크롬)로 돌기 때문에 실제 장비의 소리 지연은 잴 수 없습니다. 아래는 사람이 한 번 해 보고 결과를 적는 항목입니다. 코드는 지연을 `출력 지연 + 기본 지연 + 입력 지연 + 사용자 보정`만큼 자동으로 당겨 놓고(`src/domain/recording/latency.ts`), 맞지 않을 때를 위해 녹음 설정에 "지연 보정(ms)" 칸(−200~+200 ms, 이 브라우저에만 기억됨)을 두었습니다.

- [ ] **유선 이어폰:** 메트로놈(카운트인 4박)에 맞춰 손뼉을 4번 녹음한다. 녹음된 손뼉이 박과 ±20 ms 안에 있으면 통과.
- [ ] **블루투스 이어폰:** 같은 시험. 맞지 않으면 어긋난 만큼을 "지연 보정(ms)"에 넣어 맞는 값을 찾고, 그 값을 적어 둔다(기본 안내 문구에 반영할 값).
- [ ] **귀로 듣기(3단계 끝):** 헤드폰으로 재생하며 볼륨·EQ·딜레이·리버브 조작, 클립 이동, 재생 위치 이동. 딸깍·끊김이 들리지 않으면 통과. 새 엔진이 이미 기본(`refactor/v2`)이므로 주소 옵션 없이 그대로 듣습니다. 소리가 이상하면 같은 곡을 `?engine=v1`(옛 엔진)로도 들어 어느 쪽 문제인지 적어 둡니다.
- [ ] **내보낸 파일 듣기(P3-6):** 3분쯤의 곡(클립 2~3개, 딜레이·리버브를 켠 트랙 포함)을 "16비트·44.1 kHz"와 "24비트·48 kHz"로 한 번씩 내보내 재생기와 편집 프로그램(오디오 편집기·DAW)에서 연다. 소리가 앱에서 재생할 때와 같고(재생과 내보내기는 같은 소리 부품을 씁니다), 딸깍·잘림이 없고, 곡이 끝난 뒤 딜레이·리버브 꼬리가 자연스럽게 사라지면 통과. 자동 시험은 파일의 머리·길이·크기·최고점(−1 dBFS 이하)만 확인합니다.
- [ ] **옛 엔진 삭제(기본을 바꾼 지 1주 뒤, 설계 결정 10):** 새 엔진이 기본이 된 날(`refactor/v2`에 병합된 날)부터 1주일 동안 위 "귀로 듣기"에서 문제가 나오지 않았으면, 옛 재생 코드를 지우는 PR을 따로 올립니다. 지울 것: `BrowserAudioEngine`의 옛 `play`·`sync`·`stop`·예약 소스 보관과 옛 마스터 사슬(`audio/audioEngine.ts`), `audio/engine/engineChoice.ts`, `audio/currentEngine.ts`의 분기, `?engine=` 주소·`ad.engine` 저장소 옵션, e2e의 `E2E_ENGINE`·`E2E_P32_ENGINE`·`onNewEngine`(옛 엔진 판정 가지)과 "옛 엔진으로 돌아가는 길" 시험. `AudioEngineV2`는 `BrowserAudioEngine`을 이어받고 있으므로(디코드·음원 보관·컨텍스트 공용) 둘을 하나로 합치는 정리가 함께 필요합니다. 기다리는 1주일이 설계 결정이고 사람이 직접 들어 보고 정하는 일이라 자동으로 하지 않았습니다. 그동안 문제가 생기면 주소에 `?engine=v1`을 붙여 되돌립니다.
- [ ] **브라우저 목록(3단계·6단계 끝):** 사파리(맥), 아이폰 사파리, 안드로이드 크롬, 파이어폭스에서 업로드 → 재생 → 녹음 → 저장 → 새로고침 → 불러오기. 실패하면 지원 브라우저 표에 기록한다.
- [ ] **고해상도 화면(4단계 끝, 설계서 부록 B):** 화면 배율이 2인 기기(맥북 등)에서 분석기·파형·눈금자가 잘리거나 흐리지 않은지 본다. 파형·분석기는 화면 배율(`devicePixelRatio`)에 맞춰 그리지만 배율 2인 실제 기기에서 눈으로 본 적은 없다. 잘림이 있으면 어느 화면(분석기·파형·눈금자)인지 적어 둔다.
- [ ] **한글 입력 상태 단축키(P5-2):** 한/영 키를 한글로 둔 채 V·P·B·C(도구 바꾸기)와 Space(재생·일시정지)·Ctrl+Z(실행 취소)를 눌러 영문 상태와 같게 동작하면 통과. 이어서 템포 칸이나 트랙 이름 칸에 한글을 치는 중(글자가 조합되는 동안)에는 단축키가 반응하지 않아야 하고, 그 칸 안에서 Ctrl+S는 저장을 시작해야 합니다. 자동 시험은 한글 상태에서 오는 키 이벤트(글자 'ㅔ'·조합 중 표시)를 흉내 내어 같은 자리의 키가 같은 동작을 하는 것까지만 확인하고 실제 입력기는 쓰지 않습니다. 안 되면 쓴 입력기(윈도 기본 한글·맥 2벌식 등)와 안 되는 키를 적어 둡니다.
- [ ] **맥 ⌘ 단축키(P5-2):** 맥(크롬·사파리)에서 ⌘Z(실행 취소)·⌘Shift+Z(다시 실행)·⌘S(프로젝트 파일 저장)·⌘C·⌘V(클립 복사·붙여넣기)·⌘A(모든 클립 선택)가 Ctrl과 같게 동작하고, 메뉴·도구 단추의 키 표기가 ⌘로 보이면 통과. ⌘D·⌘E는 그 기능(복제·재생선에서 자르기)이 들어오는 P5-5에서 함께 봅니다(크롬·엣지에서 Ctrl+D·Ctrl+E의 브라우저 기본 동작을 막고 쓰는지 포함).
- [ ] **재생 화면이 부드러운지(P5-3):** 실제 화면(노트북·모니터, 가능하면 화면 배율 2인 기기도)에서 클립 2~3개로 1분쯤 재생하며 눈으로 본다. 재생선이 끊기거나 흔들리지 않고 일정하게 흐르고, 시간 표시 숫자가 재생선과 어긋나 보이지 않으며(시간 표시는 초당 30번 바뀜), 레벨 미터·분석기가 같이 움직이면 통과. 이어서 "따라가기"를 켜고 화면을 14번쯤 확대해 재생하면 재생선이 오른쪽 끝에 닿을 때 스크롤이 부드럽게 따라가야 하고(끄면 안 따라감), 재생 중 눈금자를 눌러 옮겨도 재생선이 바로 그 자리에서 이어 흘러야 합니다. 자동 시험은 재생선이 `transform`으로 움직이는 것·화면 갱신 요청 횟수·다시 그리기 횟수·글자 바뀜 횟수만 헤드리스 크롬으로 잴 뿐 사람 눈에 부드러운지는 판단하지 못합니다. 끊겨 보이면 기기·브라우저(버전)·화면 배율과 어느 순간(재생 시작·분석기를 켠 때·확대한 때)에 끊기는지를 적어 둡니다.
- [ ] **터치로 길게 누르기(P5-4):** 터치 화면(휴대폰·태블릿, 가능하면 터치 노트북)에서 클립을 0.5초쯤 꾹 누르면 클립 메뉴가 열리고(클립이 지워지거나 움직이지 않음), 손가락을 10 px 넘게 움직이면 메뉴 대신 클립이 끌리며, 트랙 머리를 꾹 눌러도 트랙 메뉴가 열려야 합니다. 메뉴 항목은 손가락으로 눌러 고를 수 있고 메뉴 밖을 누르면 닫혀야 합니다. 자동 시험은 합성 터치 포인터 이벤트(`pointerType: "touch"`)로 500 ms 시간·10 px 취소·마우스 제외까지만 확인하고, 실제 손가락과 브라우저의 꾹 누르기 기본 동작(글자 선택·돋보기·시스템 메뉴)은 확인하지 못합니다. 기본 메뉴가 같이 뜨거나 글자가 선택되면 기기·브라우저를 적어 둡니다.
- [ ] **키보드로 여는 메뉴(P5-4):** 클립에 Tab으로 초점을 주고 메뉴 키(▤)나 Shift+F10을 눌러 클립 메뉴가 열리는지 봅니다(트랙 머리는 마우스·터치로만 엽니다). 열리면 첫 항목에 초점이 있고 ↑·↓·Home·End·Enter가 동작하며, Esc로 닫으면 초점이 클립으로 돌아와야 합니다. 키보드가 보내는 우클릭 이벤트는 좌표가 브라우저마다 달라 자동 시험이 닿지 않습니다. 안 열리거나 화면 밖에 뜨면 브라우저를 적어 둡니다.
- [ ] **복제·자르기 단축키가 브라우저에 가로채이지 않는가(P5-5):** 윈도우의 크롬·엣지에서 클립을 고르고 Ctrl+D를 누르면 복제만 되고 "북마크 추가" 창이 뜨지 않으며, Ctrl+E를 누르면 자르기만 되고 주소창 검색으로 초점이 가지 않는지 봅니다. 맥(크롬·사파리)은 ⌘D·⌘E로 같은 것을 봅니다. 자동 시험은 키 이벤트가 앱에 닿았을 때 `preventDefault`가 불리는지만 확인하고, 브라우저가 앱보다 먼저 가져가는 키인지는 실제 브라우저에서만 알 수 있습니다. 새는 브라우저가 있으면 이름과 버전을 적어 둡니다.
- [ ] **파일 관리자에서 끌어다 놓기(P5-5):** 윈도우 탐색기나 맥 파인더에서 오디오 파일 하나와 여럿(2~3개)을 타임라인으로 끌어다 놓아, 놓은 트랙·시간(스냅 적용)에 클립이 생기고, 트랙 아래 빈 곳에 놓으면 새 트랙이 생기며, 끌고 들어오는 동안 놓일 자리가 보이는지 봅니다. 화면 밖(툴바·인스펙터)에 놓아도 브라우저가 파일을 열어 앱을 떠나지 않아야 합니다. 자동 시험은 합성 놓기 이벤트를 쓰므로 실제 파일 관리자가 보내는 이벤트(특히 맥과 사파리)와 같지 않을 수 있습니다.
- [ ] **3/4·6/8 메트로놈을 귀로 듣기(P5-5):** 박자표를 3/4로 바꾸고 녹음 메트로놈을 켜 카운트인을 "1마디"로 두면 높은 소리(강박)가 마디 첫 박에만 한 번, 나머지 두 박은 낮은 소리로 들리는지 봅니다. 6/8은 8분음표 간격으로 여섯 번 중 첫 번째만 높게 들려야 합니다. 자동 시험은 소리의 높이와 예약 시각만 확인하므로 박이 자연스럽게 느껴지는지는 귀로 확인합니다.
- [ ] **컴프레서 바늘을 눈으로 보기(P5-6):** 실제 곡(노래·악기 녹음 같은 큰 소리가 오르내리는 음원)으로 컴프레서를 켜고 기준 음량을 낮춰(예: −30 dB 근처) 재생합니다. 소리가 큰 곳에서는 바늘이 왼쪽(20 쪽)으로 가고 작은 곳에서는 오른쪽 끝(0)으로 돌아오며, 재생을 멈추거나 컴프레서를 끄면 바로 오른쪽 끝으로 돌아가면 통과입니다. 바늘이 너무 느리거나 떨리게 보이는지(움직임에 0.15초짜리 부드러운 전환이 붙어 있음)는 눈으로 봐야 알 수 있어 자동 시험은 압축량 값(`data-reduction`)과 목표 각도만 확인합니다. 함께 스냅 메뉴가 마디·박·1/2박·1/4박·없음 다섯 개뿐인지("메인"·"라인"·"로컬 스냅"·"글로벌 스냅"이 보이지 않는지) 한 번 봅니다.
- [ ] **장비 화면과 글자색을 눈으로 보기(P6-1):** 스타일 정리로 장비 화면(리버브·딜레이·분석기)을 오른쪽 패널 폭에 맞추고 글자색을 대비 기준(4.5:1 이상)에 맞췄습니다. 자동 시험은 "패널 밖으로 나가는 곳 0"과 "axe 색 대비 위반 0"만 재므로 눈으로 보는 일이 남았습니다. ① 곡을 올리고 클립을 고른 뒤 오른쪽 패널을 끝까지 내려 리버브 아래 줄의 '후단 이퀄라이저' 노브 3개(저음·중음·고음)가 패널 안에 보이고 마우스로 돌아가는지, 딜레이의 칸들이 눌리지 않고 줄바꿈되는지, 분석기 그림이 오른쪽에서 잘리지 않는지 봅니다(창 폭을 1024·1280·1920px로도 바꿔 봄). ② 리버브 '잔향 길이' 슬라이더에 손잡이(어두운 막대 가운데 주황 줄)가 보이고 끌면 움직이는지 봅니다. 크롬뿐 아니라 파이어폭스에서도 보이는지, 탭 키로 이 슬라이더에 왔을 때 초점 표시가 손잡이에 같이 보이는지도 봅니다. ③ 딜레이 "375 ms"·"8000 Hz"·"0.0 dB" 같은 값 글자가 `MS`·`HZ`처럼 대문자로 보이지 않고 단위가 `ms`·`Hz`·`dB` 그대로 보이는지 봅니다(딜레이·리버브·이퀄라이저·컴프레서·마스터 화면 모두). ④ 단추·메뉴 항목·입력칸에 마우스를 올렸을 때와 탭 키로 초점을 줬을 때 글자색과 바탕이 읽히는지 봅니다(자동 점검은 마우스를 올리지 않은 모습만 잼). ⑤ axe가 "판단 불가(incomplete)"로 남긴 곳은 위반이 아니라 배경이 그림·그라데이션이라 계산하지 못했다는 뜻입니다: 상태마다 18~28곳(창 폭 390·768, 높이 3200에서는 60~62곳)이 있고, 주황 바탕 단추·재생선 시간 표시·장비 화면 위 작은 이름표(5~9px. 크기는 P6-2에서 다룸)가 읽히는지 눈으로 봅니다.
- [ ] **화면 낭독기·음성 제어·키보드로 직접 해 보기(P6-2):** 접근성 작업(클립 키보드 조작·낭독 알림·단추 이름·누르는 크기)의 자동 시험은 속성·글자·크기·합성 키 입력만 확인하고, 실제 낭독 프로그램과 음성 제어는 돌리지 못합니다. ① 윈도우는 NVDA, 맥은 VoiceOver를 켜고 크롬(가능하면 사파리·엣지도)에서 앱을 엽니다. Space로 재생하면 "재생 중", 멈추면 "재생 멈춤"이, R로 녹음을 시작하면 "녹음 준비, 카운트인" → "녹음 중", 다시 R이면 "녹음 멈춤"이 한 번씩 읽혀야 합니다. 클립에 Tab으로 가면 "… 클립"과 키 안내(엔터로 고르기, 왼쪽·오른쪽 방향키로 격자 한 칸 옮기기, …)가 읽히고, ←·→ 뒤에는 "… 시작 0.25초", Shift+←·→ 뒤에는 "… 길이 7.75초", Enter·Shift+Enter 뒤에는 "… 선택됨"·"… 선택 해제"가 읽히는지 봅니다. 이퀄라이저·컴프레서·딜레이·리버브의 전원 단추는 "컴프레서 꺼짐, 토글 버튼, 눌리지 않음"처럼 읽혀야 하고(상태가 이름과 눌림 상태로 두 번 읽혀 거슬리면 프로그램 이름과 버전을 적어 둡니다), 제목 이동 키(NVDA는 H, VoiceOver는 로터)로 "반주 디자이너 2" 제목에 닿아야 합니다. ② 음성 제어(윈도우 음성 액세스, 맥 음성 제어)로 "86%" 같은 값 읽기 단추나 "꺼짐"·"켜짐" 전원 단추처럼 화면에 보이는 글자를 말해 눌러지는지 봅니다. ③ 마우스를 치우고 Tab·Shift+Tab·Enter·방향키·Esc·Ctrl+E·Ctrl+S만으로 파일 메뉴 → 오디오 업로드(실제 운영체제 파일 창까지) → 재생 → 클립 고르기 → 옮기기·길이 바꾸기 → 자르기 → 저장을 한 번 끝내 봅니다. 자동 시험은 파일 선택창을 Playwright가 대신하므로 그 창만 사람이 확인합니다. 어디서도 초점 표시가 사라지지 않는지도 함께 봅니다. ④ 알려진 한계(고치지 않았습니다): Space는 단추 위에서도 재생·멈춤이라 단추는 Enter로 눌러야 합니다. 클립의 시작점 다듬기와 페이드 손잡이는 키보드로 바꿀 수 없고(Shift+←·→는 끝점만), 노브 옆 값 글자와 클립 가장자리 손잡이는 일부러 24px보다 작게 두었습니다. ⑤ 눈으로 보기: 10px로 올린 장비 화면의 이름표가 겹치거나 잘리지 않는지, 간격을 줄인 트랙 머리와 24px로 커진 슬라이더·숫자 칸·분석기 LED·스위치가 어색하지 않은지, 커진 장비 패널(리버브 626px)이 창 폭 1024·1280·1920에서 오른쪽 패널에 들어오는지, 리버브 "공간 유형" 선택 글자가 잘리지 않는지 봅니다. 읽히지 않거나 이상하게 읽히는 곳이 있으면 프로그램·브라우저 이름과 버전을 적어 둡니다.
- [ ] **타사 화면과 닮았는지 참고 이미지와 나란히 놓고 보기(P6-3):** 타사 이름은 코드·화면에서 모두 지웠고(`grep -rniE "arturia|fl studio|t-racks|trax|specan|ableton" src` 0건. 자동 시험이 막음) 하드웨어 겉모습을 흉내 낸 장식 두 가지(리버브의 모서리 나사 4개, 빛나는 진공관 창)도 지웠습니다. 그러나 "참고 이미지와 거의 같은 배치·장식이 남았는지"는 원본 참고 이미지가 사람에게만 있어 **보지 못한 채** 판단했습니다. 앱을 열고 브라우저 높이를 충분히 늘려(오른쪽 패널의 장비 화면이 모두 보이게) 아래를 원본 이미지와 나란히 놓고 봅니다. ① 리버브 칸의 배치(RD 배지 자리, 잔향 길이 페이더와 노브의 배열) ② 분석기의 LED 점 스펙트럼(축 글자 `1K25`·`2K5`, 속도 단추 1·2·3) ③ 노브 얼굴(눈금이 둘린 원) ④ 트랙 믹스 칸의 음소거·솔로 레버 스위치 ⑤ 컴프레서의 바늘 눈금. 통과 기준: 나란히 놓았을 때 한눈에 같은 화면으로 보이는 곳이 없음. 같아 보이는 곳이 있으면 그 부분의 모양·배치를 바꾸는 작은 작업을 따로 요청합니다(법률 판단이 아니라 위험을 줄이는 확인). 참고: 트랙 믹스 칸의 이름이 `trax` → `mix`로 바뀌어, 이 칸의 펼침·접힘 기억이 업데이트 뒤 처음 한 번 기본 상태로 돌아옵니다(프로젝트 파일에는 영향 없음).

- [ ] **큰 작업으로 메모리 안내와 기준 값을 실제 기기에서 맞추기(P6-4):** 자동 시험은 머리만 큰 가짜 WAV로 "묻는다·막는다·건너뛴다"만 확인했고, 큰 곡을 실제로 올려 보지는 않았습니다. 기준 값(데스크톱 안내 600MB · 거부 1.2GB, 휴대폰 안내 200MB · 거부 400MB, 파일 하나 300MB 이상은 풀기 전에 묻기)은 설계가 "제안, 실제 기기에서 조정"이라 한 값 그대로입니다. 풀린 소리의 메모리는 길이(초) × 샘플레이트 × 채널 수 × 4바이트이고 4분 스테레오 44.1kHz는 약 85MB입니다. ① 설계의 시나리오 그대로: 4분 곡 3개를 올리고(약 255MB) 10분 길이로 이어 붙여 자르고 옮기며 편집·재생해 봅니다. 통과 기준: 버벅임이 없고 안내창이 뜨지 않음. ② 더 큰 곡을 계속 올려(예: 4분 곡 8개 이상 = 약 680MB) 600MB를 넘을 때 "메모리를 많이 씁니다"가 뜨는지, 이어서 [올리지 않기]·[그래도 올리기]가 각각 맞게 동작하는지, 약 1.2GB를 넘길 때 "올릴 수 없습니다"가 뜨는지 봅니다. 안내가 뜬 뒤에도 앱이 쓸 만하게 도는지, 탭이 죽기 전에 안내가 먼저 뜨는지가 기준이고, 너무 일찍 뜨거나 너무 늦게 뜨면 `src/domain/memory/budget.ts`의 값을 고칩니다(요청하면 제가 바꿉니다). ③ 실제 휴대폰(iPhone·Android)에서 같은 시험: 화면 폭 768px 미만이면 휴대폰 기준(200MB · 400MB)이 적용됩니다. ④ 크기가 아주 큰 WAV(300MB 이상)와 긴 mp3(1시간 이상)로 올리기 전 안내와 푼 뒤 안내가 각각 뜨는지 봅니다. 참고: `navigator.deviceMemory`는 크롬 계열에만 있고 값이 8GB까지로 잘려 나오며 다른 브라우저(사파리·파이어폭스)에는 없어서 그곳에서는 화면 폭 기준만 적용됩니다. 올리기에만 기준이 걸려 있어, 녹음(길이를 사용자가 정함)과 프로젝트 파일 열기·자동 저장 복구는 기준을 확인하지 않습니다.

## 선택: 과거 이력 정리 (설계서 P1-3, 실행하지 않음)

저장소 이력에 `node_modules` 약 103MB가 남아 있습니다. 지우려면 이력을 다시 써야 하며 **모든 커밋 번호가 바뀝니다.** 용량이 실제로 문제일 때만, 열린 PR이 없을 때, 백업 후 설계서 §6 P1-3의 `git filter-repo` 절차로 한 번에 합니다. 이 작업은 자동으로 실행하지 않았습니다.
